# zkpool-solana

> **Private SOL transfers on Solana using zero-knowledge proofs.**
> Deposit into a shared vault. Withdraw to any address. No on-chain link between the two.

## What it does

A user deposits SOL into a shared on-chain vault. In return, they receive a **deposit note** — four random secrets:

- `nullifier` — proves ownership later, used for double-spend protection.
- `secret` — part of the commitment.
- `note_secret` — binds the withdrawal to a specific recipient (anti-front-running).
- `amount` — the deposited amount (lamports).

Later, the user proves in zero knowledge that they know the secrets behind some commitment in the pool's Merkle tree, without revealing which one. The funds are withdrawn to any Solana address.

**Result:** an outside observer sees a deposit transaction and a withdrawal transaction but cannot link them.

**Technology:** Groth16 (BN254) proof generated by [Sunspot](https://github.com/reilabs/sunspot), verified by an [gnark-solana](https://github.com/Lightprotocol/gnark-solana) program deployed on Solana.

**Five principles** (why v3 exists — v2 died from a mismatch between circuit, Anchor program, and frontend):

1. **Single source of truth** — `circuits/withdrawal/spec.json`, validated by `scripts/validate-spec`.
2. **Contract checks at every boundary** — byte-level. `scripts/sync-circuits` verifies ACIR hashes.
3. **No magic numbers** — all constants from spec, propagated via `validate-spec`.
4. **LiteSVM E2E test before devnet.**
5. **Checkpoints with SHA-256.**

## Quick start

### Prerequisites

- Docker + Docker Compose
- ~5 GB free disk (Docker image + volumes)
- Solana CLI (only if you want to interact with the deployed programs)

### Run

```bash
git clone https://github.com/kwebhub/zkpool-solana
cd zkpool-solana
make up
```

After ~1 minute:

| Service | URL |
|---|---|
| Frontend | http://localhost:5173 |
| Backend | http://localhost:4001/api/health |
| Prover | http://localhost:4002/health |
| Merkle | http://localhost:4003/health |
| Prometheus | http://localhost:9090 |
| Grafana | http://localhost:3000 (`admin` / `admin`) |

### Makefile targets

```
make up          — start docker compose + merkle + prover + backend
make down        — stop all services
make reset       — stop, clear DB + Redis, restart
make status      — show running services and their health
make logs        — tail all service logs
make web         — start Vite dev server (5173)
make build       — build backend, prover, merkle, web
make clean       — remove target/, node_modules/, dist/
make exec-c CMD='...'  — run a command inside the solana container
```

## End-to-end demo

The complete flow — deposit + withdraw + double-spend protection — is scripted:

```bash
# Deposit 0.001 SOL. Prints the deposit note JSON.
make exec-c CMD='cd /home/ubuntu/scripts/e2e-deposit && ./target/release/e2e-deposit 1_000_000'

# Wait ~10s for the indexer to pick up the deposit.
# Then withdraw using the note, to any address:
make exec-c CMD='cd /home/ubuntu/scripts/e2e-withdraw && ./target/release/e2e-withdraw /tmp/note.json <RECIPIENT>'
```

See [`docs/notes/10-e2e.md`](docs/notes/10-e2e.md) for a walkthrough with real tx signatures.

## Security

Threat model — [`docs/threat-model.md`](docs/threat-model.md).

**12 attack scenarios:**
- **Protected (5):** double-spend, front-running, replay against old root, verifier substitution, vault drainage.
- **Partially (3):** XSS, rate-limit bypass, root history exhaustion.
- **Not prevented (4, documented):** corrupt tree via `new_root`, phishing frontend, malicious prover sees witness, commitment forgery (self-harm).

**Known limitations:**
- Trusted setup for Groth16 (no MPC).
- `new_root` not verified on-chain.
- Backend sees all commitments + nullifiers.
- Notes must be saved by the user (no recovery).

Found a vulnerability? See [`SECURITY.md`](SECURITY.md).
