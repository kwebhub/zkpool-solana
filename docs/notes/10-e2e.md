# 10. Full E2E (deposit → withdraw on devnet)

> **Этап 10** проекта zkpool-solana.
> Полный цикл на devnet: реальный депозит → реальный вывод. Проверка всей системы в сборе.

---

## TL;DR

Все компоненты построены (Stages 5–9). Задача Stage 10 — прогнать реальный цикл:
1. Депозит SOL в пул через on-chain программу `zk_pool`.
2. Indexer ловит событие → Postgres → Merkle tree в Redis.
3. Пользователь сохраняет note.
4. Вывод на новый адрес: сборка witness'а, генерация Groth16-пруфа через prover, on-chain верификация.
5. Проверка в Solana Explorer.

**Инструмент:** E2E-скрипты в `scripts/`. Не UI — UI протестируем в Stage 11 после port mappings.

## 10.1a. Merkle-сервис: `POST /hashes`

**Дата:** 2026-09-28
**Commit:** `e1a47a5`

### Зачем

E2E-скрипту (Rust CLI) нужны commitment и nullifier_hash из трёх входов (nullifier, secret, amount). Раньше это умел только браузер (через `noir_js` в `web/src/noir/hashes.ts`) и `hashes.json` ACIR.

**Без endpoint'а** пришлось бы либо тащить `@solana/web3.js` + `noir_js` в `services/merkle/` для Node-скрипта (десятки МБ зависимостей ради одного теста), либо дублировать крипто-логику в Rust (что нарушило бы принцип "одна реализация — везде").

**Решение:** новый endpoint `POST /hashes` в Merkle-сервисе. Тонкая обёртка над тем же ACIR, что использует браузер.

### Реализация

**`services/merkle/src/hashes.js`** — по образцу `poseidon.js`:

```javascript
const circuit = JSON.parse(readFileSync("circuits/hashes.json", "utf8"));
const noir = new Noir(circuit);

export async function computeHashes(nullifier, secret, amount) {
  const result = await noir.execute({
    nullifier: "0x" + nullifier,
    secret: "0x" + secret,
    amount: "0x" + amount,
  });
  const [commitment, nullifierHash] = result.returnValue;
  return {
    commitment: commitment.slice(2),
    nullifier_hash: nullifierHash.slice(2),
  };
}
```

**`services/merkle/src/app.js`** — новый маршрут:

```javascript
app.post("/hashes", async (req, reply) => {
  const { nullifier, secret, amount } = req.body ?? {};
  if (!isHex64(nullifier) || !isHex64(secret) || !isHex64(amount)) {
    return reply.code(400).send({
      error: "nullifier, secret and amount must be 64-char bare hex strings (no 0x)",
    });
  }
  return await computeHashes(nullifier, secret, amount);
});
```

### Формат

**Request:**
```json
{
  "nullifier": "<64 hex>",
  "secret": "<64 hex>",
  "amount": "<64 hex>"
}
```

**Response:**
```json
{
  "commitment": "<64 hex>",
  "nullifier_hash": "<64 hex>"
}
```

### Проверка

Использованы значения из Stage 3.5 `Prover.toml`:

```
POST /hashes {
  nullifier: "0000...018abef7846071c7",
  secret:    "0000...03157def08c0e38e",
  amount:    "0000...00000f4240"
}
→ {
  "commitment":     "09d9d188784ab20199a5eb7267ce27765a374ce6bc672deee9eeac9ba90b80fc",
  "nullifier_hash": "1412cc9d862599e6869a1881c8562062b98537456d9035819288219b5cd3e6e4"
}
```

Совпадает с эталоном. ✅

### Грабли

1. **Короткий hex отклоняется.** `isHex64` требует ровно 64 символа. Тестовый вызов с `018abef7846071c7` вернул 400. **Вызывающий должен padding'ить** до 64 символов.
2. **`app.js` уже импортирует `poseidon2Hash` и `merkle.js`.** Просто добавлен третий импорт. Никакой конфигурации.

### Уроки

1. **Один ACIR — три потребителя:** браузер, `services/merkle/` (Node), Rust-скрипт (через HTTP). Никаких дублирований.
2. **Merkle-сервис — уже единственный источник правды** для Poseidon2 и Merkle-дерева. Логично, что туда же уехал `/hashes`.
3. **Проверка на эталонном значении — обязательна.** Endpoint возвращает байт-в-байт то, что выдал Noir — проверено на `Prover.toml` из Stage 3.5.

## 10.1b. `scripts/e2e-deposit/` — Rust CLI

**Дата:** 2026-09-28
**Commit:** `2748d39`

### Зачем

Провести реальный депозит на devnet без браузера. Проверяет всю цепочку:
- Генерация note.
- Merkle `/hashes` (commitment + nullifier_hash).
- Backend `/api/commitments` + `/api/root-preview`.
- On-chain `deposit` instruction через raw JSON-RPC.

### Пайплайн

```
1. load keypair                   ← ~/.config/solana/id.json
2. random note                    ← rand::thread_rng, top 2 bits cleared
3. POST /hashes {nullifier, secret, amount}
   ← merkle service
4. GET /api/commitments           ← backend
5. POST /api/root-preview {commitments + new}
   ← backend → merkle /root
6. build `deposit` ix:
   [DEPOSIT_DISCRIMINATOR(8) || commitment(32) || new_root(32) || amount_le(8)]
7. getLatestBlockhash + serialize_legacy_message + sign
8. sendTransaction
9. getSignatureStatuses (poll до confirmed)
10. print note JSON
```

### Стек

```toml
[dependencies]
anyhow = "1.0"
serde = { version = "1.0", features = ["derive"] }
serde_json = "1.0"
tokio = { version = "1", features = ["full"] }
reqwest = { version = "0.12", features = ["json"] }
bs58 = "0.5"

solana-message = "4.2.4"
solana-pubkey = "3"
solana-sdk-ids = "3.1.0"
solana-signer = "3.0.1"

solana-address = { version = "~2.6.1", features = ["curve25519"] }
```

**Версии `solana-*`** — те же, что в `scripts/pool-init/` и `tests/`.

### Ключевые детали

**Random field element:**
```rust
fn random_field_hex() -> String {
    let mut bytes = [0u8; 32];
    rand::thread_rng().fill_bytes(&mut bytes);
    bytes[0] &= 0x3f;  // clear top 2 bits → stay below 2^254
    hex::encode(bytes)
}
```

**`deposit` instruction data:**
```
[0..8]   DEPOSIT_DISCRIMINATOR = [242, 35, 198, 137, 82, 225, 242, 182]
[8..40]  commitment (32 bytes)
[40..72] new_root (32 bytes)
[72..80] amount (u64 LE)
```

**Accounts:**
```
depositor  — signer, writable
pool       — PDA [b"pool3"], writable
vault      — PDA [b"vault3", pool], writable
system_program — readonly
```

### Кросс-проверка с фронтендом

Все шаги совпадают с тем, что делает браузер (Stages 9.6b, 9.7b):
- Note: `generateNote.ts`.
- Hashes: `noir/hashes.ts` (тоже через `/hashes` — единственная реализация).
- Root preview: `useDeposit.ts` → `postRootPreview`.
- Instruction: Codama генерирует **тот же** layout.

### Грабли

1. **`Pubkey::derive_program_address` возвращает `Option`, не `Result`.** `.context(...)` работает на `Option` через `anyhow::Context`. Компилятор подсказал `.ok_or(...)` — но `.context()` эквивалентен.
2. **`solana-message::Message::serialize` под `wincode` feature.** Ручная сериализация в `serialize_legacy_message` (как в `pool-init`, Stage 8.2).
3. **`solana-transaction` не подключаем** — та же проблема с `wincode`, что в `pool-init`.

### Уроки

1. **E2E через CLI — воспроизводимо.** Не зависит от браузера, кошелька, UI. Полезно для CI (Stage 12).
2. **`/hashes` endpoint — критичен.** Без него пришлось бы тащить `noir_js` в Rust, что нарушило бы принцип "одна реализация крипто — везде".
3. **Копирование 60 строк `serialize_legacy_message`** из `pool-init` в `e2e-deposit` — осознанное дублирование. Общий crate — преждевременная абстракция для двух мест. Когда появится третье — вынести.

### Критическая бага и фикс

**Первая попытка депозита упала:**

```
POST /hashes returned error 500
Value 0x31020e14...1706 exceeds field modulus
Values must fall within [0, 21888242871839275222246405745257275088548364400416034343698204186575808495617)
```

**Причина:** `random_field_hex()` очищал только **топ-2 бита** (`& 0x3f`), оставляя верхний байт до `0x3f`. Но модуль BN254 начинается с `0x30`. Значения `0x31`–`0x3f` — **больше модуля**.

**Фикс:** очищать **топ-3 бита** (`& 0x1f`), гарантируя верхний байт ≤ `0x1f < 0x30`.

```rust
// Было:
bytes[0] &= 0x3f;  // max 0x3f — может превышать 0x30
// Стало:
bytes[0] &= 0x1f;  // max 0x1f — гарантированно < 0x30
```

**Тот же фикс** в `web/src/deposit/generateNote.ts`.

### Грабли

1. **`& 0x3f` недостаточно.** Интуитивная маска "очистить топ-2 бита, чтобы влезть в 254 бита" — неверна, потому что модуль BN254 начинается с `0x30`, а не с `0x40`. Нужно `& 0x1f`.
2. **Ошибка от `noir_js` невнятная.** "Expected witness values to be integers, but '31020e...' failed with 'invalid digit found in string'" (при попытке передать over-prime) — вводит в заблуждение. Правильная ошибка пришла от Rust-эндпоинта: "exceeds field modulus".
3. **`services/merkle/src/hashes.js`** — endpoint работает как relay. Ошибка возникла внутри `noir_js`, но 500 пришёл именно от Merkle-сервиса.

### Уроки

1. **Маска для field reduction должна учитывать первое слово модуля.** Для BN254 `p = 0x30644e72...` — верхний байт `0x30`, поэтому `& 0x1f` (или `& 0x0f` для запаса) — безопасно.
2. **E2E-скрипты находят баги, которые не ловят unit-тесты.** Тесты `reduce_to_field` работали корректно, но **генерация** random field element была неверной. Только реальный прогон через noir_js выявил проблему.
3. **Симметричный фикс во фронтенде — обязателен.** Один и тот же алгоритм в двух местах. Если бы оставили только Rust — фронтенд сломался бы при следующем депозите из браузера.

## 10.2. `scripts/e2e-withdraw/` + полный цикл на devnet

**Дата:** 2026-09-28
**Commit:** `1f6da41`

# 🎉 Полный E2E пройден.

Реальный депозит → реальный вывод. Groth16-пруф верифицирован on-chain.

**Deposit tx:** `5LzXwAGJVLLnHprCDSkWYemYzWbkMZiffHH8r3UcWR5HCP44pUSGedoUAqc1UgGkLMXtixJv87TtKx4iDX32xXLL`
**Withdraw tx:** `5f3LqrCJx6FkSGYRFgQ1cjk9KRadBv2LfA6mNQtULL4XBBDzUp2pxkbhr8QGXmuUqwVxt6Hc8y5Y2ueJTJqbkSe7`

### Пайплайн

```
1. Read note from JSON file
2. Reduce recipient → BN254 field   ← zk_pool::encoding::reduce_to_field
3. recipient_binding = hash_2(note_secret, recipient_reduced)  ← Merkle /hash
4. leaf_index lookup в /api/commitments
5. Merkle proof, is_even из /api/proof
6. root из /api/root
7. POST /api/withdraw → base64 proof + public witness
8. ComputeBudget setComputeUnitLimit(400_000)
9. Build `withdraw` ix + send
```

### Data layout `withdraw` (Anchor Borsh)

```
[disc(8)]
|| proof: Vec<u8> = u32 LE length (4) + bytes (324)
|| nullifier_hash: [u8; 32]
|| root: [u8; 32]
|| recipient: Pubkey (32)
|| amount: u64 LE (8)
|| recipient_binding: [u8; 32]
```

### Accounts (7)

```
payer           — signer, writable
pool            — PDA [b"pool3"]
nullifier_record — PDA [b"nullifier_record", pool, nullifier_hash]
vault           — PDA [b"vault3", pool]
to              — writable (recipient)
verifier_program — readonly
system_program  — readonly
```

### Три бага, которые нашли и починили

**1. Отсутствовал u32 length-prefix для `Vec<u8>` proof.**

Симптом: `memory allocation failed, out of memory` при входе в инструкцию.
Причина: Anchor Borsh десериализует `Vec<u8>` как `u32 LE length + bytes`. Мы писали proof без 4-байтовой длины — Anchor читал длину из первых 4 байт пруфа, получал огромное число, пытался аллоцировать.
Фикс: `ix_data.extend_from_slice(&(proof_bytes.len() as u32).to_le_bytes())` перед proof.

**2. Seed `NULLIFIER_RECORD_SEED` = `b"nullifier_record"`, не `b"nullifier3"`.**

Симптом: `ConstraintSeeds. Left: HaviR... Right: DNfyZ...`.
Причина: я угадал `b"nullifier3"` по аналогии с `b"pool3"` / `b"vault3"`. Но `nullifier_record` не имеет суффикса "3".
Фикс: прочитать `constants.rs`.

**3. Compute budget exceeded (200k).**

Симптом: `ComputationalBudgetExceeded`, но с логом `Proof verified successfully!`.
Причина: верификатор Groth16 съел 182k CU из 200k. Программе не хватило на создание PDA и перевод lamports.
Фикс: prepend `ComputeBudgetInstruction::SetComputeUnitLimit(400_000)`.

### Кросс-проверка

**Verifier log:**
```
Program 5t51iu6apRxgLbt91eVZ6YYzHsnmBCVnLGqJtqdfMFWJ invoke [2]
Program log: Proof verified successfully!
Program 5t51iu6apRxgLbt91eVZ6YYzHsnmBCVnLGqJtqdfMFWJ consumed 181562 of 181689 compute units
```

**Это тот же verifier-программ, что был задеплоен в Stage 3.4.** Тот же Groth16-пруф, что валидировался в Stage 7.7 через `sunspot verify`.

### Грабли

1. **`zk_pool::encoding::reduce_to_field` публичен** — импортирован через `use zk_pool::encoding::reduce_to_field;`. Никакого дублирования.
2. **`e2e-withdraw` линкует `zk_pool` crate** — тянет за собой anchor-lang, solana-program. Сборка 50 сек (vs. 1 сек у e2e-deposit). Приемлемо для теста.
3. **Default CU budget 200k — мало для Groth16.** Типичная практика — 400k–1.4M. Мы ставим 400k.
4. **`ComputeBudget111111111111111111111111111111`** — hardcoded, без новой зависимости. Instruction data: `[2, u32 LE limit]`.

### Уроки

1. **Anchor Borsh: `Vec<u8>` всегда с `u32 LE` length prefix.** `[u8; N]` — без prefix. Смешение → OOM или неверная десериализация.
2. **Seed-константы versioned — не всегда.** `pool3`, `vault3` — да. `nullifier_record` — нет. **Всегда читать `constants.rs`.**
3. **Groth16-верификация ≈ 182k CU.** Оставлять запас. Compute budget — обязательный шаг для ZK-транзакций.
4. **E2E находит баги, которые unit-тесты пропускают.** Все три бага — интеграционные, проявляются только при реальной отправке.
