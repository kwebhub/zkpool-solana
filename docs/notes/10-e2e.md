# 10. Full E2E (deposit → withdraw on devnet)

> **Этап 10** проекта zkpool-solana.
> Полный цикл на devnet: реальный депозит → реальный вывод. Проверка всей системы в сборе.

---

## TL;DR

Все компоненты построены (Stages 5–9). Задача Stage 10 — прогнать реальный цикл:
1. Депозит SOL в пул через on-chain программу `zk_pool`.
2. Indexer ловит событие → Postgres → Merkle tree в Redis.
3. Пользователь сохраняет note.
4. Вывод на новый адрес: сборка witness'а, генерация Groth16-пруфа через prover, on-chain верификация.
5. Проверка в Solana Explorer.

**Инструмент:** E2E-скрипты в `scripts/`. Не UI — UI протестируем в Stage 11 после port mappings.

## 10.1a. Merkle-сервис: `POST /hashes`

**Дата:** 2026-09-28
**Commit:** `e1a47a5`

### Зачем

E2E-скрипту (Rust CLI) нужны commitment и nullifier_hash из трёх входов (nullifier, secret, amount). Раньше это умел только браузер (через `noir_js` в `web/src/noir/hashes.ts`) и `hashes.json` ACIR.

**Без endpoint'а** пришлось бы либо тащить `@solana/web3.js` + `noir_js` в `services/merkle/` для Node-скрипта (десятки МБ зависимостей ради одного теста), либо дублировать крипто-логику в Rust (что нарушило бы принцип "одна реализация — везде").

**Решение:** новый endpoint `POST /hashes` в Merkle-сервисе. Тонкая обёртка над тем же ACIR, что использует браузер.

### Реализация

**`services/merkle/src/hashes.js`** — по образцу `poseidon.js`:

```javascript
const circuit = JSON.parse(readFileSync("circuits/hashes.json", "utf8"));
const noir = new Noir(circuit);

export async function computeHashes(nullifier, secret, amount) {
  const result = await noir.execute({
    nullifier: "0x" + nullifier,
    secret: "0x" + secret,
    amount: "0x" + amount,
  });
  const [commitment, nullifierHash] = result.returnValue;
  return {
    commitment: commitment.slice(2),
    nullifier_hash: nullifierHash.slice(2),
  };
}
```

**`services/merkle/src/app.js`** — новый маршрут:

```javascript
app.post("/hashes", async (req, reply) => {
  const { nullifier, secret, amount } = req.body ?? {};
  if (!isHex64(nullifier) || !isHex64(secret) || !isHex64(amount)) {
    return reply.code(400).send({
      error: "nullifier, secret and amount must be 64-char bare hex strings (no 0x)",
    });
  }
  return await computeHashes(nullifier, secret, amount);
});
```

### Формат

**Request:**
```json
{
  "nullifier": "<64 hex>",
  "secret": "<64 hex>",
  "amount": "<64 hex>"
}
```

**Response:**
```json
{
  "commitment": "<64 hex>",
  "nullifier_hash": "<64 hex>"
}
```

### Проверка

Использованы значения из Stage 3.5 `Prover.toml`:

```
POST /hashes {
  nullifier: "0000...018abef7846071c7",
  secret:    "0000...03157def08c0e38e",
  amount:    "0000...00000f4240"
}
→ {
  "commitment":     "09d9d188784ab20199a5eb7267ce27765a374ce6bc672deee9eeac9ba90b80fc",
  "nullifier_hash": "1412cc9d862599e6869a1881c8562062b98537456d9035819288219b5cd3e6e4"
}
```

Совпадает с эталоном. ✅

### Грабли

1. **Короткий hex отклоняется.** `isHex64` требует ровно 64 символа. Тестовый вызов с `018abef7846071c7` вернул 400. **Вызывающий должен padding'ить** до 64 символов.
2. **`app.js` уже импортирует `poseidon2Hash` и `merkle.js`.** Просто добавлен третий импорт. Никакой конфигурации.

### Уроки

1. **Один ACIR — три потребителя:** браузер, `services/merkle/` (Node), Rust-скрипт (через HTTP). Никаких дублирований.
2. **Merkle-сервис — уже единственный источник правды** для Poseidon2 и Merkle-дерева. Логично, что туда же уехал `/hashes`.
3. **Проверка на эталонном значении — обязательна.** Endpoint возвращает байт-в-байт то, что выдал Noir — проверено на `Prover.toml` из Stage 3.5.
