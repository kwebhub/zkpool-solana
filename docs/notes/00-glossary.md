## 1. Криптография с нулевым разглашением (ZK)

### ZK proof (доказательство с нулевым разглашением)

Способ **доказать**, что ты знаешь некоторый секрет, **не раскрывая** сам секрет. Пример: доказать, что ты знаешь пароль от двери, не называя пароль.

**В нашем проекте:** пользователь доказывает, что знает секреты **некоторого депозита** в пуле, не раскрывая **какого именно**. Это обеспечивает приватность: нельзя связать депозит с выводом.

### Circuit (схема, ZK-схема)

Программа, которая описывает, **что именно** доказывается. Состоит из:
- **входов** (публичных и приватных),
- **ограничений** (constraints) — правил, которым должны удовлетворять входы,
- **выходов**.

**Аналогия:** circuit — как математическая формула. «Докажи, что `x² = 4` и `x > 0`». Ты можешь доказать это, не называя `x` (это `2`).

**В нашем проекте:** circuit `withdrawal` доказывает три утверждения (C1, C2, C3).

### Публичный вход (public input)

Значение, которое **видят все**, включая verifier. В circuit объявляется с ключевым словом `pub`.

**В нашем проекте (5 публичных):** `root`, `nullifier_hash`, `recipient`, `recipient_binding`, `amount`.

### Приватный вход (private input)

Значение, которое **скрыто** от всех, кроме prover (того, кто генерирует proof). В Noir — без `pub`.

**В нашем проекте (5 приватных):** `nullifier`, `secret`, `note_secret`, `merkle_proof[20]`, `is_even[20]`.

### Witness (свидетельство)

**Полный набор** входных данных для circuit'а, включая **приватные**. Без witness **нельзя** сгенерировать proof.

**Аналогия:** если circuit — формула, witness — конкретное решение. Например, для `x² = 4, x > 0` witness — это `x = 2`.

**В нашем проекте:** witness содержит все 10 входов (5 публичных + 5 приватных). Сохраняется в `withdrawal.gz`.

### Constraint (ограничение)

Условие, которому должно удовлетворять доказательство. Если хотя бы одно constraint не выполнено — proof **невалиден**.

**В нашем проекте (3):**
- C1: `hash_1(nullifier) == nullifier_hash`.
- C2: `hash_2(note_secret, recipient) == recipient_binding`.
- C3: `compute_merkle_root(hash_3(nullifier, secret, amount), merkle_proof, is_even) == root`.

**В нашем circuit'е — 6308 constraints** (Poseidon2 внутри разворачивается в много ограничений).

### Prover (доказывающий)

Сторона, которая **генерирует** proof. Знает witness.

**В нашем проекте:** сервис `services/prover` (Rust + Sunspot).

### Verifier (проверяющий)

Сторона, которая **проверяет** proof. Не знает witness, видит только публичные входы.

**В нашем проекте:** on-chain verifier program (Solana BPF, отдельная программа).

### Commitment (обязательство)

Криптографический хеш, который **фиксирует** данные, не раскрывая их.

**Формула в проекте:** `commitment = hash_3(nullifier, secret, amount)`.

**Свойство:** из commitment **невозможно** восстановить `nullifier`, `secret` или `amount`. Но если у тебя есть эти секреты — ты можешь **проверить**, что commitment им соответствует.

### Nullifier (обнулитель)

Секретное число, которое **помечает** депозит как **потраченный** при выводе. Хранится **только** у пользователя.

**Зачем:** защита от **double-spend** (двойной траты). Каждый депозит можно вывести **один раз**. Nullifier_hash записывается on-chain при первом выводе, и повторный вывод с тем же nullifier_hash **отклоняется**.

### Nullifier hash (`nullifier_hash`)

**Публичный** хеш от nullifier. Публикуется on-chain при выводе.

**Формула:** `nullifier_hash = hash_1(nullifier)`.

**Используется:**
- как публичный вход circuit'а,
- как seed для PDA `NullifierRecord` (защита от double-spend),
- как ключ в БД backend.

## 2. Хеш-функции и структуры данных

### Хеш-функция

Функция, которая превращает **произвольные** данные в **фиксированное** число. Свойства:
- **Детерминирована:** одинаковый вход → одинаковый выход.
- **Односторонняя:** по выходу **нельзя** восстановить вход.
- **Устойчива к коллизиям:** сложно найти два разных входа с одинаковым выходом.

**Примеры:** SHA-256, Keccak, Poseidon.

### Poseidon2

**Хеш-функция**, оптимизированная для **ZK-схем**. Работает с элементами **поля** (не с байтами). Внутри circuit Poseidon2 занимает **меньше** constraints, чем SHA-256, — а значит, proof генерируется **быстрее** и весит **меньше**.

**Почему не SHA-256:** SHA-256 использует побитовые операции, которые **дорого** выражаются в арифметике поля. Poseidon2 использует только сложение и умножение в поле — дёшево.

**В нашем проекте:** через `poseidon2_permutation` (builtin в Noir).

### Перестановка (permutation)

**Обратимая** функция, которая перемешивает состояние. Poseidon2 построен на перестановке, которая применяется к состоянию **из 4 элементов** (`t = 4`).

### Rate и capacity

Параметры sponge-конструкции (способа строить хеш из перестановки).

- **Rate (r):** сколько элементов можно использовать для данных. У нас `r = 3`.
- **Capacity (c):** сколько элементов зарезервировано для безопасности. У нас `c = 1`.
- **Правило:** `t = r + c`. У нас `t = 4`.

**Почему это важно:** если использовать **все** 4 слота как вход (`rate = 4`, `capacity = 0`) — криптостойкость **теряется**. Поэтому у нас `hash_1`, `hash_2`, `hash_3`, но **не** `hash_4`.

### Zero-padding (дополнение нулями)

Способ обрабатывать меньше данных, чем помещается в state. Для `hash_1(x)` state = `[x, 0, 0, 0]`. Для `hash_2(x, y)` state = `[x, y, 0, 0]`. Для `hash_3(x, y, z)` state = `[x, y, z, 0]`.

**Побочный эффект:** `hash_1(x) == hash_2(x, 0)` и `hash_2(x, y) == hash_3(x, y, 0)`. Это **не баг** — прямое следствие zero-padding. В нашем проекте это **безопасно**, потому что мы никогда не хешируем одно и то же значение разными функциями в одном контексте.

### BN254 (Baby Jubjub / BN254 field)

**Кривая** (elliptic curve), над которой работают Groth16 и Noir. Модуль поля — огромное число:

```
21888242871839275222246405745257275088548364400416034343698204186575808495617
```

Это ≈ **2^254**. Все значения `Field` в Noir должны быть **меньше** этого числа.

**Следствие:** Solana Pubkey (32 байта = 256 бит) **не влезает** в Field. Нужна **редукция**: `reduce_to_field(pubkey_bytes) = pubkey_bytes mod BN254_prime`.

### Merkle tree

**Двоичное дерево**, где каждый лист — хеш блока данных, а каждый родитель — хеш от конкатенации двух детей. Корень дерева (root) — **один** хеш, представляющий **всё** дерево.

**Свойство:** изменить любой лист → изменится root.

**В нашем проекте:** глубина 20 → до 2^20 ≈ 1 млн листьев (депозитов).

### Merkle proof

**Набор хешей**, который позволяет **проверить**, что конкретный лист принадлежит дереву с известным root.

**Размер:** `log2(количество_листьев)`. Для дерева глубины 20 — **20 хешей**.

**В нашем проекте:** `merkle_proof[20]` — приватный вход.

### Merkle root

**Корень** Merkle tree. Один хеш, представляющий всё дерево.

**В нашем проекте:** `root` — публичный вход circuit'а.

### `is_even` (флаг стороны)

Для каждого уровня Merkle tree — **булев флаг**: наш узел **слева** (`true`) или **справа** (`false`)?

**Почему важно:** Poseidon2 **не коммутативен**: `hash_2(a, b) != hash_2(b, a)`. Если перепутать `left` и `right`, root не сойдётся.

## 3. Noir и ZK-схемы

### Noir

**Язык программирования** для ZK-схем. Разработан Aztec. Похож на Rust, но **специализирован** для доказательств: компилируется в ACIR, работает с полями, имеет встроенные ZK-примитивы (Poseidon2, Merkle proof, и т.д.).

### Nargo

**CLI-инструмент** для Noir. Аналог `cargo` для Rust. Команды:
- `nargo init` — создать проект.
- `nargo test` — запустить тесты.
- `nargo compile` — скомпилировать в ACIR.
- `nargo execute` — сгенерировать witness.

### ACIR (Abstract Circuit Intermediate Representation)

**Промежуточное представление** circuit'а после компиляции Noir. Содержит:
- описание входов,
- constraints,
- байткод для witness generation.

**Файл:** `withdrawal.json` (41 КБ).

### `Nargo.toml`

**Манифест** Noir-проекта (аналог `Cargo.toml` в Rust). Содержит:
- имя пакета,
- тип (`bin` — circuit, `lib` — библиотека),
- зависимости (например, `poseidon = { path = "../poseidon" }`).

### `main.nr`

**Главный файл** Noir-проекта. Содержит функцию `main()` — точку входа circuit'а.

### `pub` (ключевое слово)

В Noir обозначает **публичный** параметр функции. Без `pub` — приватный.

**Особенность:** `main()` в `type = "bin"` **обязан** иметь `pub` на **возвращаемом типе**. Verifier не может получить приватный witness, поэтому без `pub` outputs недостижимы.

### `Field` (тип)

**Элемент поля** BN254. Число от 0 до `21888...616` (≈ 2^254).

**Важно:** `Field` **не** то же самое, что `u64` или `u256`. Это **элемент поля**, а не целое число. Разница проявляется в переполнении (overflow): `Field` «заворачивается» по модулю.

### `global`

**Константа** времени компиляции в Noir. Например: `global TREE_DEPTH: u32 = 20;`.

### Const generics

**Параметры типа** размера массива. Например: `fn compute_merkle_root<let DEPTH: u32>(...) -> Field`. Позволяет одной функции работать с массивами **любого** размера, зафиксированного на этапе компиляции.

### `poseidon2_permutation`

**Встроенная функция** Noir для Poseidon2. Сигнатура в nargo 1.0.0-rc.2 — **один аргумент**: массив `[Field; 4]`. Размер state выводится из размера массива.

**Важно:** **НЕ** `poseidon2_permutation(state, 4)`. Просто `poseidon2_permutation(state)`.

## 4. Groth16 и Sunspot

### Groth16

**Протокол ZK-доказательств**. Преимущества:
- **Компактный proof** — 324 байта в нашем случае.
- **Быстрая верификация** — 1.25 секунды.
- **On-chain friendly** — proof влезает в Solana-транзакцию.

**Недостаток:** требует **trusted setup** (см. ниже).

**Альтернативы** (STARK, PLONK) — proof **большой**, не влезает в tx Solana.

### Trusted setup

**Разовая** процедура генерации **proving key** и **verifying key** из constraint system.

**Проблема:** во время setup генерируется **toxic waste** — промежуточные значения. Если их **сохранить**, можно **подделывать** proof, которые verifier примет.

**В нашем проекте:** setup делается **одной стороной** (нами). Для **devnet/demo** это **приемлемо**. Для **production** — нужна **MPC ceremony** (см. `docs/DEMO-NOTICE.md`).

### MPC ceremony (Multi-Party Computation ceremony)

Процедура trusted setup, в которой участвует **много** независимых сторон. Каждая вносит **свой** вклад. Итоговый toxic waste **никто** не знает — потому что для этого нужно было бы, чтобы **все** стороны сговорились.

**В нашем проекте:** **не проводится**. Это demo-проект.

### CCS (Constraint System)

**Constraint System** — представление circuit'а для Groth16. Более **низкоуровневое**, чем ACIR. Содержит constraints и переменные в форме, удобной для генерации ключей.

**Файл:** `withdrawal.ccs` (642 КБ).

### Proving key (`.pk`)

**Ключ** для генерации proof. Используется prover'ом. **Секретный** (не должен попасть к атакующему).

**В нашем проекте:** `withdrawal.pk` (2 145 109 байт ≈ 2 МБ).

### Verifying key (`.vk`)

**Ключ** для проверки proof. Используется verifier'ом. **Публичный**.

**В нашем проекте:** `withdrawal.vk` (972 байта).

### Sunspot

**CLI-инструмент** от Reilabs для компиляции Noir circuit в Solana verifier program. Пайплайн:
1. `sunspot compile` — ACIR → CCS.
2. `sunspot setup` — CCS → PK + VK.
3. `sunspot deploy` — VK → Solana verifier program.
4. `sunspot prove` — witness + PK + CCS → proof.
5. `sunspot verify` — proof + VK → true/false.

### Public witness (`.pw`)

**Публичная часть** witness'а, которую verifier получает вместе с proof'ом.

**В нашем проекте:** `withdrawal.pw` (172 байта) — это **точно тот же формат**, что `encode_public_inputs` в on-chain программе.

### Proof (`.proof`)

**Сам ZK-proof**. В Groth16 — 324 байта.

## 5. Solana

### Solana

**Блокчейн** с высокой пропускной способностью. Транзакции обрабатываются **параллельно** (Sealevel), комиссии низкие.

**Наш проект:** devnet (тестовая сеть).

### Program (программа)

**Смарт-контракт** в Solana. Хранится как **аккаунт** с исполняемым кодом.

**У нас две программы:**
- `zk_pool` — основная (пул).
- verifier — проверка ZK-proof.

### BPF (Berkeley Packet Filter)

**Формат** байткода, который исполняет Solana. Компилируется из Rust через `cargo build-sbf`.

**Почему BPF:** безопасное исполнение без доступа к памяти хоста.

### Program ID

**Публичный адрес** программы в Solana. Не меняется при обновлении кода (если authority сохраняет keypair).

**У нас:** `5t51iu6apRxgLbt91eVZ6YYzHsnmBCVnLGqJtqdfMFWJ` (verifier).

### ProgramData

**Отдельный аккаунт**, где хранится **код** upgradeable-программы. Program ID — это **ссылка**, ProgramData — **данные**.

**Зачем разделение:** позволяет обновлять код программы, не меняя её адреса.

### Upgrade authority

**Адрес**, который имеет право **обновлять** программу. У нас — наш кошелёк. В production — multisig + timelock.

### Rent (аренда)

**Плата** за хранение данных в Solana. Аккаунт должен иметь баланс ≥ rent-exempt минимум.

**У нас:** verifier ~87 КБ → 0.444 SOL rent.

### PDA (Program Derived Address)

**Адрес**, который **не имеет** приватного ключа и **вычисляется** из seeds + program ID.

**Формула:** `PDA = hash(seeds, program_id, "ProgramDerivedAddress")`.

**У нас три PDA:**
- `pool`: seeds `["pool3"]`.
- `vault`: seeds `["vault3", pool]`.
- `nullifier_record`: seeds `["nullifier_record", pool, nullifier_hash]`.

### CPI (Cross-Program Invocation)

**Вызов** одной программы из **другой**.

**У нас:** `zk_pool` вызывает verifier через CPI.

### Transaction (транзакция)

**Набор инструкций**, которые выполняются атомарно (всё или ничего).

### Instruction (инструкция)

**Один вызов** программы с аккаунтами и данными.

### Discriminator (дискриминатор)

**Первые 8 байт** в instruction data — уникальный идентификатор типа инструкции. Anchor использует их автоматически.

**У нас:** `pool`, `deposit`, `withdraw` — три разных дискриминатора.

## 6. Наш проект: доменные термины

### Deposit note (нота депозита)

**Набор секретов**, который пользователь получает при депозите и **хранит локально**. Без note **нельзя** вывести средства.

**Содержит:**
- `nullifier` — секрет для double-spend.
- `secret` — секрет для commitment.
- `note_secret` — секрет для recipient_binding.
- `amount` — сумма в lamports.
- `commitment` — хеш, записанный в Merkle tree.

**Формат в проекте:** plaintext в `localStorage`. В production — **должно** быть зашифровано.

### Pool

**Пул** — общий vault, куда пользователи депонируют SOL. При выводе SOL берётся из vault.

**PDA:** `["pool3"]`.

### Vault

**Хранилище SOL** в пуле. Отдельный PDA, чтобы SOL не смешивался с данными pool'а.

**PDA:** `["vault3", pool]`.

### `recipient_binding`

**Привязка** получателя к proof'у. Формула: `hash_2(note_secret, recipient)`.

**Зачем:** защита от **front-running**. Без binding атакующий может **скопировать** proof и **подменить** recipient на свой. С binding — proof **привязан** к конкретному recipient'у, и подмена **ломает** constraint C2.

### Front-running

**Атака**, при которой злоумышленник **видит** чужую транзакцию и отправляет **свою** с **более высокой** комиссией, чтобы она прошла **раньше**.

**В нашем проекте:** защита через `recipient_binding`.

### Double-spend

**Атака**, при которой один и тот же депозит **выводится дважды**.

**Защита:** `nullifier_hash` записывается on-chain при первом выводе. Повторный вывод **отклоняется**.

### `TREE_DEPTH`

**Глубина Merkle tree.** У нас — 20. Максимум листьев — 2^20 ≈ 1 млн.

**Хранится в:** `spec.json` (`circuit.tree_depth`), circuit (`global TREE_DEPTH`), on-chain (`constants::TREE_DEPTH`). Все три значения **должны совпадать**.

### `spec.json`

**Единый источник истины** для публичных входов, приватных входов, constraints, witness layout. Лежит в `circuits/withdrawal/spec.json`.

**Зачем:** в v2 порядок публичных входов задавался в трёх местах (circuit, Anchor, frontend), и рассинхрон приводил к `InvalidInstructionData`. В v3 — единый файл + валидатор.

### `validate-spec`

**Rust CLI** в `scripts/validate-spec/`. Читает `spec.json` и **проверяет** 15 правил внутренней согласованности. Запускается вручную, из Makefile и CI.

### `sync-circuits`

**Rust CLI** в `scripts/sync-circuits/`. Компилирует Noir circuit'ы и **синхронизирует** JSON в потребителей (`services/merkle/circuits/`, `web/public/circuits/`). Два режима:
- `--check` (для CI) — mismatch = ошибка.
- `--apply` (для локальной разработки) — mismatch = копирование.

## 7. Инструменты разработки

### Rust

**Язык программирования**. Используется в backend, prover, sync-circuits, validate-spec, on-chain программе.

### Cargo

**Менеджер пакетов** и сборщик Rust. Аналог `npm` для Node.js.

### Anchor

**Фреймворк** для Solana-программ на Rust. Упрощает:
- определение аккаунтов,
- обработку инструкций,
- сериализацию/десериализацию данных,
- генерацию IDL.

### IDL (Interface Description Language)

**JSON-описание** интерфейса Anchor-программы: инструкции, аккаунты, события.

**Зачем:** на его основе Codama генерирует **TypeScript-клиент** для frontend.

### Codama

**Инструмент** для генерации клиентского кода из IDL. Заменяет собой старый `@coral-xyz/anchor`-клиент.

### pnpm

**Менеджер пакетов** для Node.js. Быстрее и **экономнее** по месту, чем `npm`/`yarn` (использует hard links).

### Vite

**Сборщик** для frontend. Быстрый dev-сервер, HMR.

### Vue 3

**JS-фреймворк** для frontend.

### Pinia

**State manager** для Vue. Заменяет Vuex.

### Noir JS (`@noir-lang/noir_js`)

**JS-обёртка** над ACVM (виртуальной машиной Noir). Позволяет выполнять ACIR-файл **в браузере** — например, для генерации witness на клиенте.

### Docker

**Контейнеризация**. Все инструменты (Rust, Solana CLI, Anchor, Nargo, Sunspot, Node.js) — в **одном** контейнере `solana-zkpool-solana`.

### tmux

**Терминальный мультиплексор.** Используется в `Makefile` для запуска сервисов в фоне.

### Prometheus / Grafana

**Системы мониторинга.** Prometheus собирает метрики, Grafana рисует дашборды.

### SHA-256

**Криптографический хеш.** Используется в `.checkpoints/` для сверки артефактов. Устойчив к коллизиям → если хеши совпадают, файлы **идентичны** побайтово.
